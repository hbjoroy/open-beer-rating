# Local Development Setup

> Backend migration/testing update: see [BACKEND_MIGRATION.md](BACKEND_MIGRATION.md). On this Windows host prefer `wslc` after inspecting its help. The Podman database bootstrap below is legacy; do not use its reset path against existing data.

## Prerequisites

- **Podman** (for PostgreSQL)
- **Rust** toolchain with `wasm32-unknown-unknown` target
- **Trunk** (`cargo install trunk`)

## Quick Start

```powershell
# 1. Start PostgreSQL (podman container, port 5432)
.\scripts\start-db.ps1

# 2. Run migrations
.\scripts\migrate-db.ps1 -EnvFile .env

# 3. Start the API server (terminal 1)
cargo run -p open-tappd-api

# 4. Start the frontend dev server (terminal 2)
cd crates\web
trunk serve --open
```

The frontend runs on `http://localhost:8080` and proxies `/api/` to the backend on `http://localhost:3000`.

## Environment

- `.env` is auto-generated by `start-db.ps1` with secure random keys
- WebAuthn rpId defaults to `localhost`, origin defaults to `http://localhost:8080`
- `RUST_LOG=info,open_tappd_api=debug` for backend debugging

## Reset

```powershell
# Destroy DB and start fresh
.\scripts\start-db.ps1 -Reset
.\scripts\migrate-db.ps1 -EnvFile .env
```

## Database Access

Use psql inside the container:

```powershell
podman exec -it opentappd-db psql -U opentappd -d opentappd
```

Useful queries:

```sql
-- List all users
SELECT id, username, display_name, created_at FROM users;

-- List all passkeys with user info
SELECT p.id, u.username, p.name, p.created_at, length(p.credential_id) as cred_len
FROM user_passkeys p JOIN users u ON u.id = p.user_id
ORDER BY u.username, p.created_at;

-- Count passkeys per user
SELECT u.username, COUNT(p.id) as passkey_count
FROM users u LEFT JOIN user_passkeys p ON p.user_id = u.id
GROUP BY u.username;

-- Delete all passkeys for a user (use for testing)
DELETE FROM user_passkeys WHERE user_id = (SELECT id FROM users WHERE username = 'NAME');
```

## Architecture (local)

```
Browser (localhost:8080)
  └─ Trunk dev server (serves WASM + static)
       └─ Proxy /api/ → localhost:3000
             └─ Axum API server (cargo run -p open-tappd-api)
                  └─ PostgreSQL (podman, localhost:5432)
```

## WebAuthn / Passkey Testing

### Browser build verification

Run `rustup target add wasm32-unknown-unknown`, then
`cargo check -p open-tappd-web --target wasm32-unknown-unknown --locked`.
Run `trunk build --locked` from `crates/web` for the actual browser bundle.
On Windows ARM64, if Trunk cannot download a matching wasm-bindgen binary,
put the official Windows x64 wasm-bindgen CLI matching Cargo.lock on PATH
(currently 0.2.121). It runs through Windows emulation. Verify the release checksum.
Start the API with STATIC_DIR pointing at the existing `crates/web/dist` directory
to test deep links through the production SPA fallback.

The 2026-10-28 local verification used PostgreSQL 17 via wslc, 72 passing workspace
tests including ignored database tests, and an actual Trunk/WASM build. Browser
checks use synthetic local data; they do not substitute for real-device passkey
testing. Recovery-only login keeps the token in memory, so reloading requires
sign-in again; tasting drafts remain scoped to the account in session storage.

### Device checks

- rpId: `localhost`
- Origin: `http://localhost:8080` (must match Trunk serve address)
- Passkeys created locally use Windows Hello / platform authenticator
- Each `navigator.credentials.create()` with same (rpId, user.id) should replace old credential on device
- If duplicates appear in device picker: clear from Windows Settings → Accounts → Passkeys

## Physical Android camera smoke test

Use the separate **Take a photo** control on the tasting form. It is a native
file input with `accept="image/*"` and `capture="environment"`: supporting mobile
browsers open their camera, while others may offer a picker. **Choose from library**
accepts JPEG, PNG, WebP, HEIC and HEIF. No continuous camera stream or third-party
conversion service is used. HEIC previews are generated by the server after upload.

For LAN testing, bind a test-only API instance to the computer's private LAN IPv4
address and a separate port, using the existing local test database and STATIC_DIR.
Keep the production database and public tunnelling out of this test. The mobile
must be on the same Wi-Fi; Windows firewall or Wi-Fi client isolation may block
access. Recovery-key sign-in can test this native capture flow over local HTTP;
WebAuthn/passkeys need a properly trusted HTTPS origin and matching RP settings.
Do not disable browser security checks or trust an arbitrary certificate.

On the phone: open the LAN URL, sign in to a disposable test account, choose a
beer and score, take a photo, accept the camera result, and save. Verify the
thumbnail and enlarged photo in history, portrait orientation, cancellation of
capture, and retry after an interrupted upload. Desktop upload tests cannot
confirm that the phone's camera actually opens; record the browser/device result.
